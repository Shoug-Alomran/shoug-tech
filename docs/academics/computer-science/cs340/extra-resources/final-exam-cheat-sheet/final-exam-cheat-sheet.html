CH 1–2

Database concepts and architecture

Definitions

  • Database: a collection of related data. DBMS: software to define, build, manipulate and share it.
  • DB approach vs files: self-describing (catalog/metadata), program–data independence, multiple views, shared concurrent access, less redundancy, integrity, backup.
  • Actors: DBA, designers, end users, system analysts and programmers.

Three-schema architecture

  • External (user views) → conceptual (whole DB logically) → internal (physical storage).
  • Logical data independence: change the conceptual schema without changing views. Physical: change storage without changing the conceptual schema.
  • Schema (structure, rarely changes) vs instance/state (data at a moment).

Languages and models

  • DDL (define), DML (manipulate), DCL (grant/revoke).
  • Data models: conceptual (ER), representational (relational), physical.
  • Architectures: centralized, client-server (2-tier, 3-tier with an application server).
CH 03

ER and EER modeling

ER notation

  • Entity (rectangle), weak entity (double rectangle, identified through its owner with a partial key, dashed underline).
  • Attributes (ovals): key (underlined), composite, multivalued (double oval), derived (dashed oval).
  • Relationship (diamond; identifying relationship = double diamond).

Constraints on relationships

  • Cardinality ratio: 1:1, 1:N, M:N.
  • Participation: total (double line, every entity must participate) vs partial (single line).
  • (min, max) notation is the alternative.
Read the cardinality from each side: "an employee works for one department; a department has many employees" = 1:N with N on the employee side.

EER

  • Specialization / generalization with superclass and subclasses (inheritance).
  • Disjoint (d) vs overlapping (o); total vs partial specialization.
  • Categories (union types).
CH 4–5

Relational model and ER-to-relational mapping

Terms

Relation (table), tuple (row), attribute (column), domain, degree (number of attributes), cardinality (number of tuples). Superkey ⊇ candidate key (minimal) → one chosen as primary key.

Constraints

  • Domain, key (unique), entity integrity (PK not null), referential integrity (FK matches an existing PK or is null).
  • Violations: insert can break all four; delete can break referential (handle by restrict, cascade, set null); update can break key/referential.

Mapping algorithm

  1. Strong entity → table, simple attributes, PK.
  2. Weak entity → table with the owner's PK as FK + partial key → composite PK.
  3. 1:1 → FK on the total-participation side.
  4. 1:N → FK on the N side.
  5. M:N → new table with both PKs (composite PK) + relationship attributes.
  6. Multivalued attribute → new table (PK of entity + the value).
  7. N-ary relationship → new table with all participating PKs.

EER: superclass/subclass → separate tables sharing the PK (or one table with a type attribute).

Composite attributes become their simple parts; derived attributes are usually not stored.
CH 6–7

SQL

DDL

CREATE TABLE Employee (
  ssn   CHAR(9) PRIMARY KEY,
  name  VARCHAR(30) NOT NULL,
  salary DECIMAL(10,2) CHECK (salary > 0),
  dno   INT,
  FOREIGN KEY (dno) REFERENCES Department(dnumber)
     ON DELETE SET NULL ON UPDATE CASCADE );
ALTER TABLE Employee ADD email VARCHAR(50);
DROP TABLE Employee CASCADE;

Query skeleton

SELECT   d.dname, COUNT(*) AS n, AVG(e.salary)
FROM     Employee e JOIN Department d ON e.dno = d.dnumber
WHERE    e.salary > 3000          -- filters rows
GROUP BY d.dname
HAVING   COUNT(*) > 2             -- filters groups
ORDER BY n DESC;
Execution order: FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY.

Useful pieces

  • DISTINCT, LIKE 'A%' (% any, _ one char), BETWEEN, IN (...), IS NULL.
  • Joins: inner, LEFT/RIGHT/FULL OUTER, natural, self-join (aliases).
  • Set operations: UNION, INTERSECT, EXCEPT.
  • Aggregates: COUNT, SUM, AVG, MIN, MAX (ignore NULLs, except COUNT(*)).

Nested queries

  • WHERE salary > (SELECT AVG(salary) FROM Employee)
  • IN / NOT IN, EXISTS / NOT EXISTS (correlated), > ALL, > ANY.
  • Division ("employees who work on all projects"): NOT EXISTS (… EXCEPT …).
A non-aggregated column in SELECT must appear in GROUP BY. = NULL is never true: use IS NULL. Use HAVING (not WHERE) for conditions on aggregates.

Changes and views

  • INSERT INTO T VALUES (...), UPDATE T SET a = ... WHERE ..., DELETE FROM T WHERE ....
  • CREATE VIEW v AS SELECT ... (virtual table). Assertions and triggers enforce complex rules.
CH 09

Normalization

Functional dependencies

X → Y: equal X values imply equal Y values.

  • Armstrong: reflexivity, augmentation, transitivity (+ union, decomposition).
  • Closure X⁺: all attributes determined by X; X is a key if X⁺ = all attributes (and minimal).

Normal forms

FormRuleRemoves
1NFAtomic values, no repeating groupsMultivalued cells
2NF1NF + no partial dependency on part of a composite keyPartial dependencies
3NF2NF + no transitive dependency (non-key → non-key)Transitive dependencies
BCNFEvery determinant is a superkeyRemaining anomalies
"The key, the whole key, and nothing but the key."

Worked example

R(StudentID, CourseID, StudentName, Grade, Instructor, InstrOffice)
FDs: StudentID -> StudentName
     StudentID, CourseID -> Grade
     CourseID -> Instructor
     Instructor -> InstrOffice
Key: (StudentID, CourseID)
2NF: Student(StudentID, StudentName)
     Course(CourseID, Instructor, InstrOffice)
     Enroll(StudentID, CourseID, Grade)
3NF: split Course -> Course(CourseID, Instructor)
                      Instructor(Instructor, InstrOffice)

Why normalize

Removes redundancy and update, insert and delete anomalies. Decompositions must be lossless join (and ideally dependency-preserving).

CH 10

NoSQL and object-oriented databases

NoSQL

  • For big, distributed, flexible-schema data; scale out horizontally.
  • Types: key-value (Redis, DynamoDB), document (MongoDB, JSON), column-family (Cassandra, HBase), graph (Neo4j).
  • CAP theorem: in a partition, choose consistency or availability. Many NoSQL systems use eventual consistency (BASE vs ACID).

Object databases

Objects with identity (OID), encapsulation, inheritance and complex types; ODMG standard, OQL. Object-relational systems add these to SQL.

ACID

Atomicity, consistency, isolation, durability: the transaction guarantees relational DBMSs provide.

Practice

Where does the FK go in a 1:N relationship?

Answer
In the table on the N side.
Practice

How is an M:N relationship mapped?

Answer
A new table holding both primary keys (as a composite PK) and the relationship's attributes.
Practice

Which constraint says a primary key cannot be NULL?

Answer
Entity integrity
Practice

WHERE vs HAVING?

Answer
WHERE filters rows before grouping; HAVING filters groups after aggregation.
Practice

Write: names of departments with more than 5 employees.

Answer
SELECT d.dname FROM Department d JOIN Employee e ON e.dno = d.dnumber GROUP BY d.dname HAVING COUNT(*) > 5;
Practice

Write: employees earning more than the average salary.

Answer
SELECT name FROM Employee WHERE salary > (SELECT AVG(salary) FROM Employee);
Practice

Why does WHERE phone = NULL return nothing?

Answer
NULL comparisons are unknown; use IS NULL.
Practice

Logical vs physical data independence?

Answer
Logical: change the conceptual schema without changing user views. Physical: change storage without changing the conceptual schema.
Practice

R(A, B, C, D), key AB, FD B → C. Highest normal form?

Answer
1NF: B → C is a partial dependency.
Practice

R(A, B, C), key A, FD B → C. Which normal form fails?

Answer
3NF (transitive A → B → C); it is in 2NF.
Practice

What is BCNF?

Answer
Every determinant of a non-trivial FD is a superkey.
Practice

How is a multivalued attribute mapped?

Answer
A separate table with the entity's PK and the attribute value.
Practice

Double line between an entity and a relationship means?

Answer
Total participation
Practice

Which NoSQL type stores JSON-like records?

Answer
Document stores (e.g. MongoDB)
Practice

Degree vs cardinality of a relation?

Answer
Degree = number of attributes; cardinality = number of tuples.
Practice

ON DELETE CASCADE does what?

Answer
Deleting the referenced row also deletes the rows that reference it.
