CH 01

Software engineering and ethics

Definitions

  • Software engineering: an engineering discipline concerned with all aspects of software production, from specification to maintenance.
  • Software = programs + documentation + configuration data.
  • Essential attributes: maintainability, dependability and security, efficiency, acceptability.
  • Generic products (market) vs customized products (one customer).

Activities and types

  • Four fundamental activities: specification, development (design + implementation), validation, evolution.
  • Application types: stand-alone, interactive transaction-based, embedded control, batch, entertainment, modelling/simulation, data collection, systems of systems.

Ethics (ACM/IEEE)

Confidentiality, competence, intellectual property rights, computer misuse. The code's eight principles: public, client and employer, product, judgment, management, profession, colleagues, self.

Process activities

  • Requirements: feasibility → elicitation and analysis → specification → validation.
  • Design: architectural, database, interface, component.
  • Validation: development testing → system testing → acceptance testing.
  • Evolution: change is inevitable.

Coping with change

Change anticipation (prototyping) and change tolerance (incremental delivery). Process improvement: CMMI levels (initial → managed → defined → quantitatively managed → optimizing).

CH 03

Agile software engineering

Agile manifesto

Individuals and interactions over processes and tools · working software over comprehensive documentation · customer collaboration over contract negotiation · responding to change over following a plan.

XP practices

User stories, small releases, test-first development, refactoring, pair programming, continuous integration, collective ownership, sustainable pace, on-site customer, simple design.

Scrum

  • Roles: product owner (backlog, priorities), Scrum master (removes impediments, coaches), development team.
  • Artifacts: product backlog, sprint backlog, potentially shippable increment.
  • Events: sprint (2–4 weeks), planning, daily scrum (15 min), review, retrospective.
  • Velocity tracks points done per sprint; burndown charts track remaining work.

Plan-driven vs agile

Choose plan-driven for detailed upfront specs, large distributed teams, regulation and safety; agile for small co-located teams, changing requirements and an available customer.

CH 04

Software project management

Concerns

Deliver on time, within budget, meeting expectations; keep the team working well. Activities: proposal writing, planning, risk management, people management, reporting.

Risk management

  • Risk types: project (schedule, resources), product (quality, performance), business (organization, market).
  • Process: identification → analysis (probability, effects) → planning (avoid, minimize, contingency) → monitoring.

Planning and people

  • Gantt charts and activity networks; milestones and deliverables.
  • Estimation: experience-based and algorithmic (COCOMO II).
  • People factors: consistency, respect, inclusion, honesty; group cohesiveness; communication.
CH 05

Requirements engineering

Types

  • User requirements: natural language and diagrams for customers. System requirements: detailed specification for developers.
  • Functional: what the system does ("shall allow users to search").
  • Non-functional: qualities and constraints: product (performance, usability, security, reliability), organizational (process, standards), external (legal, ethical).
"The system shall respond within 2 seconds" is non-functional (performance), even though it mentions a system action.

Process

Elicitation (interviews, observation/ethnography, scenarios, use cases) → specification (SRS, structured natural language, use cases) → validation (validity, consistency, completeness, realism, verifiability; reviews, prototyping, test-case generation) → management (traceability, change).

Good requirements

Unambiguous, testable/verifiable, consistent, complete, traceable. Non-functional requirements should be measurable (metrics: response time, MTTF, availability %).

CH 06

Software design and UML

UML diagrams

  • Use case: actors and goals. Activity: workflow. Sequence: object interactions over time.
  • Class: classes, attributes, operations and relationships. State machine: states and events.
  • Context models show the system boundary.

Class relationships

  • Association (line), aggregation (hollow diamond, part can exist alone), composition (filled diamond, part dies with the whole), generalization (hollow triangle, inheritance), dependency (dashed arrow), realization (dashed + hollow triangle).
  • Multiplicity: 1, 0..1, *, 1..*.

Architecture and patterns

  • Architectural patterns: layered, repository, client-server, pipe-and-filter, MVC.
  • Design patterns: Observer, Singleton, Factory, Adapter, Facade.
  • Good design: high cohesion, low coupling, information hiding.
CH 7–8

Implementation and testing

Implementation issues

Reuse (abstraction, object, component, system levels), configuration management (version control, system integration, problem tracking, release management), host-target development, open source licensing (GPL, LGPL, BSD).

Verification vs validation

  • Verification: "are we building the product right?" (meets the spec).
  • Validation: "are we building the right product?" (meets the user's needs).
  • Inspections are static; testing is dynamic.

Testing levels

  • Development testing: unit → component → system testing.
  • Release testing: by a separate team, requirements-based, scenario, performance.
  • User testing: alpha (at the developer), beta (real users), acceptance (customer decides).
  • TDD: write the test first, then code to pass it, refactor.
  • Regression testing re-runs tests after changes.
