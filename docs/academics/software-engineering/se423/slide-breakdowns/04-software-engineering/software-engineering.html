Build the product right,
and build the right product.

Software engineering covers every aspect of software production, from early specification to maintaining the system after it goes into use, with project management running across all of it. This chapter contrasts project-based and product-based engineering, walks the process models and life cycles from waterfall to agile and DevOps, and then turns to product engineering: quality attributes, the product vision, product management, prototyping and customer value.

01 — SOFTWARE ENGINEERING

An engineering discipline for all of software production

Software engineering is concerned with all aspects of software production, from the early stages of system specification through to maintaining the system after it has gone into use.

Software engineering and project management
The engineering flow is Analyze → Design → Build → Test → Deliver: requirements definition; system and software design; implementation and unit testing; integration and system testing; operation and maintenance. Project management spans all five stages.
Core activities and constraints
Specification defines need and constraints · development designs and implements · validation checks fitness · evolution adapts after delivery.

The three constraints, scope, time and cost, interact, with quality and risk across all three: changing one needs an explicit trade-off.
Exam lens: verification asks “did we build the product right?” Validation asks “did we build the right product?”
02 — PRODUCT VS PROJECT SOFTWARE ENGINEERING

Who owns the requirements?

Software products are generic systems that provide functionality useful to a range of customers: large business systems (MS Excel), personal products (Evernote), simple apps and games (Sudoku). Product engineering methods evolved from techniques for one-off custom systems, which large businesses, government and public bodies still need, developed in dedicated projects. A project is a temporary endeavor undertaken to create a unique product, service or result.

Project-based software engineering
Triangle: the customer's problem generates requirements (owned by customer and developer), which are implemented by software (the developer) that helps with the problem.

• the starting point is a set of software requirements owned by an external client
• a software company (the contractor) designs and implements the system to meet them
• the customer may change requirements at any time, and usually does; the contractor must follow
• custom software usually has a long lifetime (10+ years) and must be supported over it
Product-based software engineering
Triangle: an opportunity inspires product features, implemented by software that realizes the opportunity, and the developer owns all three.

• the starting point is a business opportunity spotted by people or a company
• the company designs and implements features that will be useful to customers
• the developer decides the timescale, which features to include and when the product changes
• rapid delivery is essential to capture the market

Software execution models

where the software runs
Model What runs where
Stand-alone The software runs entirely on the customer's computers; the vendor's servers only provide product updates
Hybrid Part of the functionality runs on the customer's computer and some on the developer's servers (e.g. backups, extra features)
Software as a service All functionality runs on the developer's servers; customers use a browser or mobile app

Product manager vs project manager

different jobs
Product manager Project manager
Idea validation, setting the vision, product planning and strategy Scope planning, budgeting
Market analysis, marketing strategy, technology roadmap Team organization, task management, progress updates
User needs analysis, product launch Management of resources, risks and issues
They overlap on things like communication with the team and customers, but the product manager owns what and why, the project manager owns how and when.
03 — SOFTWARE PROCESS MODELS

Waterfall, incremental, reuse, prototyping and improvement

Model Idea
Waterfall Takes specification, development, validation and evolution and makes them separate phases: requirements definition → system and software design → implementation and unit testing → integration and system testing → operation and maintenance
Incremental development Interleaves specification, development and validation, running concurrently from an outline description; the system grows as a series of versions (initial → intermediate → final), each adding functionality
Integration and configuration Relies on reusable components or systems; development configures them for a new setting and integrates them
Incremental delivery
Define outline requirements → assign requirements to increments → design the system architecture → develop an increment → validate, integrate and validate the system → deploy the increment. If the system is incomplete, develop the next increment; when complete, it is the final system.
Reuse-oriented software engineering
Requirements specification → software discovery and evaluation → requirements refinement. Then, if an application system is available, configure it; if components are available, adapt them or develop new ones, and integrate the system.
Prototype development
Step Output
Establish prototype objectives Prototyping plan
Define prototype functionality Outline definition
Develop prototype Executable prototype
Evaluate prototype Evaluation report
Plan-based vs agile
Plan-based: requirements engineering produces a requirements specification that drives design and implementation; changes come back as change requests.
Agile: requirements engineering and design/implementation loop together continuously.

Process improvement and capability maturity

04 — LIFE CYCLES

From predictive to agile

Four shapes
Predictive: analyze → design → build → test → deliver, once.
Iterative: analyze, then repeated analyze/design (prototype) and build/test (refine) loops, then deliver.
Varying-sized increments: each increment runs the whole analyze→deliver cycle and ships something.
Agile: short, repeated, delivering cycles.
Iteration-based vs flow-based agile
Iteration-based: fixed time-boxes, each doing requirements, analysis, design, build and test for the work selected.
Flow-based: no fixed time-box; work moves through the same steps limited by the number of features in the WIP (work in progress) limit, repeating as needed.
The continuum of life cycles
Plotted on degree of change (x) and frequency of delivery (y): predictive is low/low, iterative high change but low delivery, incremental frequent delivery but low change, agile high on both.
Uncertainty and complexity (Stacey model)
Axes: requirements uncertainty and technical uncertainty. Simple (low/low) suits linear approaches; complicated and complex suit adaptive approaches; chaos (high/high) is fundamentally risky.

Characteristics of the four categories

Iterative Dynamic Repeated until correct Single delivery Correctness of solution
Incremental Dynamic Performed once for a given increment Frequent smaller deliveries Speed
Agile Dynamic Repeated until correct Frequent smaller deliveries Customer value via frequent deliveries and feedback
05 — DEVOPS

One multi-skilled team for development, deployment and support

DevOps joins development and operations through shared ownership, automation, measurement and learning.

DevOps automation
Continuous integration: integrate small changes often; each triggers an automated build and tests.
Continuous delivery: every passing change is deployable; production release stays a business decision.
Continuous deployment: passing changes go to production automatically; monitoring and rollback are essential.
Infrastructure as code: environments defined and created from code.
Code management and measurement
The code management system around a code repository: branching and merging, recovering version information, saving and retrieving versions, transferring code to and from developers' file stores.

DevOps measurement: data collection → data analysis → report generation. Useful measures: lead time, deployment frequency, change failure rate, recovery time.
CI/CD pipeline: commit → build → automated tests → security checks → deploy → observe.
06 — PRODUCT ENGINEERING

Quality attributes, product lines and platforms

Seven software product quality attributes
1. Reliability · 2. Availability · 3. Resilience · 4. Maintainability · 5. Responsiveness · 6. Usability · 7. Security
Software product line
A set of products that share a common core; each member adds customer-specific adaptations. Product lines can implement a custom system for a customer whose needs a generic product can't meet.
Platform
A software (or software + hardware) product with functionality that lets new applications be built on it. Example: Facebook, which offers product features and also supports “Facebook apps” that businesses or interest groups use.
Comparable software development
The key feature of product development: no external customer generates requirements or pays. Comparable cases: student projects (the group decides the features), research software (built to answer research questions), and internal tool development (for your own organization's employees).
07 — THE PRODUCT VISION

Every product starts with one

The starting point for product development is a product vision: a simple statement of the essence of the product.

🎯
Memory hook
What · Who · Why
The vision answers three questions: what is the product to be developed? Who are the target customers and users? Why should customers buy this product?
Moore's vision template
FOR (target customer)
WHO (statement of the need or opportunity)
The (product name) is a (product category)
THAT (key benefit, compelling reason to buy)
UNLIKE (primary competitive alternative)
OUR PRODUCT (statement of primary differentiation)
Example: CRM-Innovator
“FOR a mid-sized company's marketing and sales departments WHO need basic CRM functionality, THE CRM-Innovator is a web-based service THAT provides sales tracking, lead generation and sales representative support features that improve customer relationships at critical touch points. UNLIKE other services or packaged software, OUR product provides very capable services at a moderate cost.”

Information sources for a product vision

four sources
Source How it helps
Domain experience Developers who work in an area (say marketing and sales) know what software support it needs, and may be frustrated by gaps in the software they use
Product experience Users of existing software see simpler, better ways to provide the same functionality; new products can use new technology such as speech interfaces
Customer experience Discussions with prospective customers reveal their problems, constraints such as interoperability, and the critical attributes they need
Prototyping and playing around Build a prototype to understand an idea better and experiment with variations on it as a platform
iLearn vision: “FOR teachers and educators WHO need a way to help students use web-based learning resources and applications, THE iLearn system is an open learning environment THAT allows the resources used by classes and students to be easily configured by teachers. UNLIKE virtual learning environments such as Moodle, the focus of iLearn is the learning process rather than administering materials, assessments and coursework. OUR product lets teachers create subject- and age-specific environments using any web-based resources.”
08 — SOFTWARE PRODUCT MANAGEMENT

The product manager sits between business, customers and developers

Software product management is a business activity focused on the products a business develops and sells. Product managers (PMs) take overall responsibility for the product and are involved in planning, development and marketing, from first conception to withdrawal from the market. They look outward to customers rather than at the software itself.

Product management concerns
Business needs: the software must meet the company's business goals.
Technology constraints: make developers aware of technology issues that matter to customers.
Customer experience: stay in regular contact with customers to understand what they want, who the users are and how the product will be used.
Technical interactions of product managers
• Product vision management: help develop the vision, assess changes against it, prevent vision drift
• Product roadmap development: the plan for development, release and marketing; the PM is the final authority on changes
• User stories and scenarios: refine the vision and identify features; the PM leads them
• Product backlog: the prioritized to-do list; the PM helps create, refine and prioritize it
• Acceptance testing: verify a release meets the roadmap's goals and is efficient and reliable
• Customer testing: give customers a release and gather feedback on features, usability and business fit
• User interface design: act as a surrogate user so features aren't needlessly complex
09 — PRODUCT PROTOTYPING

Build something people can react to

Product prototyping is developing an early version of a product to test your ideas and convince yourself and funders that it has real market potential.

Why prototype
• users only really relate to a product when they see a working version, then say what they like and suggest features
• a prototype helps identify fundamental components or services and test technology
• building one should be the first thing you do, aiming for a version that demonstrates the key features
• always plan to throw it away and re-implement properly, taking account of security and reliability
Two-stage prototyping
1. Feasibility demonstration: an executable system that shows the new ideas work, and shows funders or management the features that beat competitors.

2. Customer demonstration: extend the feasibility prototype with ideas for specific customer features and how they are realized. First do user studies so you know your users and scenarios.
10 — CUSTOMER VALUE AND THE BUSINESS MODEL

Value is benefits minus costs, as the customer sees them

Value is the sum of the tangible and intangible benefits and costs.

Customer perceived value
Customer perceived value = total customer benefit − total customer cost.

Benefits: product, services, personnel, image.
Costs: monetary, time, energy, psychological.
Business model canvas (in filling order)
1 Customer segments · 2 Value proposition · 3 Channels · 4 Customer relationships · 5 Revenue streams · 6 Key resources · 7 Key activities · 8 Key partners · 9 Cost structure
Summary of the chapter: products may be stand-alone, hybrid or service-based; in product engineering the same company decides the features and implements them. A product vision says what is being built, for whom, and why they'd buy it, drawing on domain, product and customer experience and prototypes. Product managers own the vision and roadmap, user stories and backlog, customer and acceptance testing and UI design, and they connect the business, the developers and the customers. Always prototype to refine ideas and demonstrate features.
11 — AGILE DELIVERY AND IMPROVEMENT

Scrum in brief, and Plan-Do-Check-Act

Material from class that goes with this chapter (and the Old Chapter 2 quiz).

Scrum roles and artifacts
Product Owner: value and backlog order · Scrum Master: team effectiveness and removing impediments · Developers: create a done increment.

Product backlog → product goal · sprint backlog → sprint goal · increment → definition of done.

Agile is not “no plan, no documentation, no architecture”: planning is continuous and design evolves with feedback.
Lifecycle trade-offs
Approach Best fit Main risk
Waterfall Stable requirements, regulated gates Late feedback, costly change
Incremental Value can ship in slices Architecture can erode
Iterative Solution needs refinement Convergence is not automatic
Spiral Large, high-risk work Complex and management-heavy
Agile High change, close customer access Needs discipline and engagement
Plan-Do-Check-Act: Plan a measurable problem and a small experiment · Do it on a limited scope and capture evidence · Check the results against the hypothesis · Act: standardize, adapt or abandon, then repeat.

COMMON MISTAKES

Where exam answers usually go wrong

6 places this chapter's terms get mixed up.

1. Who owns the requirements
✗ WRONG“In product-based SE the customer owns the requirements.”
✓ RIGHTIn project-based SE the external client owns them; in product-based SE the developer owns the features.
2. Product vs project manager
✗ WRONGTreating product manager and project manager as the same role.
✓ RIGHTThe product manager owns the vision, roadmap and market; the project manager owns scope, budget, schedule and resources.
3. Hybrid vs SaaS
✗ WRONG“Hybrid means the software runs in the cloud.”
✓ RIGHTHybrid splits functionality between the customer's computer and the vendor's servers; SaaS runs everything on the vendor's servers.
4. Iterative vs incremental
✗ WRONGUsing the two words interchangeably.
✓ RIGHTIterative refines the solution through repetition (single delivery); incremental ships usable slices (frequent deliveries).
5. Goal of each life cycle
✗ WRONG“Agile's goal is speed.”
✓ RIGHTIncremental's goal is speed; agile's is customer value through frequent deliveries and feedback.
6. Keeping the prototype
✗ WRONGShipping the prototype as the product.
✓ RIGHTPlan to throw the prototype away and re-implement, accounting for security and reliability.
