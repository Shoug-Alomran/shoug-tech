Overview

Quality Attributes: Scenarios, Tactics and Design Decisions

Functional requirements say what the system does; quality attributes say how well it does it, and the plan for meeting them lives in the architecture. Because quality words are vague and overlap (is a denial-of-service attack an availability, performance or security problem?), qualities are pinned down with quality attribute scenarios: six parts from source to response measure. Tactics are the design techniques that achieve a scenario’s response, and the lecture ends with the seven categories of design decision through which an architect shapes quality.

QA vs. functional

Functional = what the system shall do (planned in detailed design). Quality = criteria for judging the system as a whole (planned in the architecture).

Six-part scenario

Source, stimulus, environment, artifact, response, response measure. The measure is what makes it testable.

Tactics

Primitive, proven design techniques that control a quality attribute response (redundancy, caching…).

Seven decision types

Responsibilities, coordination, data model, resources, binding time, technology, mapping.

Slide 3 / 18

Architecture and Requirements

Notes

  1. 1

    Functional requirements state what the system must do, usually written as “the system shall …”. Each defines a specific behaviour or function.

  2. 2

    The plan for implementing functional requirements is produced in the detailed design.

  3. 3

    Non-functional requirements, also called quality attributes (QA), are criteria for judging how the system operates as a whole, not a specific behaviour: speed, reliability, security…

  4. 4

    The plan for implementing them is detailed in the architecture. That split (functions → detailed design, qualities → architecture) is the reason architecture spends so much effort on quality.

Exam angle

Past exam · Quiz 1 · 261 · Q14 (true/false)Q1

Software architecture is concerned only with functional structure and does not need to consider non-functional requirements.

Show answer

False — Architecture must address important quality attributes such as performance, security and availability; their plan lives in the architecture.

Slide 4 / 18

Architecture and Requirements

Notes

  1. 1

    Quality has to be considered in every phase: design, implementation and deployment. A fast architecture can still be ruined by slow code or a badly configured server.

  2. 2

    Architecture cannot achieve qualities on its own. It provides the foundation, but the foundation is useless if the details in later phases are ignored (the same point as Chapter 2: architecture alone cannot guarantee quality).

Slide 5 / 18

Architecture and Requirements

Notes

  1. 1

    Architecture documents are read by many stakeholders: developers, managers, sales, testers, support, maintenance staff and customers.

  2. 2

    Each has their own opinion about which quality matters most, so the architect has to weigh them against each other.

  3. 3

    The development team cares about maintainability (easy to change) more than the customer does; the QA team cares about testability.

  4. 4

    The end user (the slide’s question) mostly cares about qualities they can feel: usability, performance and availability.

Exam angle

PredictionQ1

Show answer

QA: testability. Development team: maintainability (modifiability).

Slide 6 / 18

Quality Attribute Considerations

Notes

  1. 1

    Quality attributes are constraints on the manner in which the system implements and delivers its functionality: they say how a function must be achieved, not what it is.

  2. 2

    They are used as criteria to evaluate the system during and after development: efficiency, availability, scalability, adaptability, security, dependability…

  3. 3

    Take one functional requirement: “when the user presses the green button, the Options dialog appears”. The function is the same in every case below; only the quality constraint changes.

  4. 4

    A performance QA says how quickly the dialog appears; an availability QA says how often this function may fail; a usability QA says how easy the function is to learn.

Exam angle

PredictionQ1

For the requirement “when the user presses the green button the Options dialog appears”, write one performance and one usability quality requirement.

Show answer

Performance: the dialog appears within 0.5 seconds of the press. Usability: a first-time user can find and open the dialog without help in under 10 seconds.

Slide 7 / 18

Quality Attribute Considerations Scenarios

Notes

  1. 1

    Quality attribute words have unstable definitions and overlapping concerns: people mean different things by “reliable” or “secure”.

  2. 2

    The DoS example shows the overlap: a denial-of-service attack makes the system down (availability), very slow (performance), is an attack (security) and stops users reaching the service (usability). Which quality does it “belong” to?

  3. 3

    The solution is to characterise qualities with quality attribute scenarios: concrete stories with a stimulus, a response and a measure, instead of vague words.

  4. 4

    Real example: if the payment server crashes during a transaction (stimulus), the system switches to a backup within 2 seconds (response), keeping 99.99% uptime (measure). That is clear, testable and no longer overlaps with other qualities.

Slide 8 / 18

A quality attribute scenario has the

Notes

  1. 1

    Stimulus: a condition that needs to be considered when it arrives at the system: a request, a failure, an attack, a change request.

  2. 2

    Source of stimulus: the entity that generates it: a human, another computer system, an internal component.

  3. 3

    Environment: the conditions the system is in when the stimulus occurs: normal operation, overload, start-up, maintenance.

  4. 4

    Artifact: the element of the system that is stimulated: the whole system, a database, a server, the UI, the code.

  5. 5

    Response: the activity the system undertakes after the stimulus arrives: process it, log it, fail over, deny access.

  6. 6

    Response measure: the response must be measurable, so the requirement can be tested: response time under 2 seconds, 99% uptime, repair within 30 minutes. A scenario without a measure is not testable.

Exam angle

Past exam · Quiz 1 · 261 · Q22 (matching)Q1

Match each quality attribute scenario element with its meaning: source, stimulus, artifact, environment, response, response measure.

Show answer

Source → entity that generates the stimulus. Stimulus → event or condition that affects the system. Artifact → system element affected by the stimulus. Environment → condition under which the stimulus occurs. Response → what the system does after the stimulus. Response measure → measurable criterion used to evaluate the response.

Slide 9 / 18

A Quality Attribute Scenario Template

Notes

  1. 1

    The one-sentence template: some source generates some event (stimulus) that arrives at some artifact under some conditions (environment) and must be dealt with (response) in a satisfactory way (response measure). Write any scenario by filling these six slots in this order. Source: who or what generates the stimulus. Stimulus: the event or condition that arrives. Environment: the conditions the system is in when it arrives. Artifact: the part of the system that is stimulated. Response: what the system does. Response measure: how the response is measured, so the requirement can be tested.

Exam angle

Past exam · Midterm 261 · Q10 · 3 marksQ1

Online Voting System: “During an election, thousands of eligible voters access the Online Voting System to submit their votes. While the system is operating under heavy election-day traffic, a voter submits a vote for a selected candidate. The system must validate the voter, securely record the vote, prevent duplicate voting, and display a confirmation message. The complete voting transaction must be processed within 4 seconds for at least 95% of voting requests.” Identify the six elements of the quality attribute scenario.

Show answer

Source: eligible voters. Stimulus: submitting a vote for a selected candidate. Environment: heavy election-day traffic. Artifact: the Online Voting System. Response: validate the voter, securely record the vote, prevent duplicate voting and display a confirmation. Response measure: processed within 4 seconds for at least 95% of voting requests.

The system processes the request and displays matching course sections. The search results must be displayed within 2 seconds for at least 95% of requests.” Match the six elements.

Show answer

Source: enrolled student. Stimulus: submits a course search request. Artifact: university registration system. Environment: peak registration time. Response: processes the request and displays matching course sections. Response measure: results displayed within 2 seconds for at least 95% of requests.

Slide 11 / 18

Quality Attribute Scenarios: a maintainability example

Notes

  1. 1

    A maintainability (modifiability) scenario. Here the “stimulus” is not a failure or a request but a wish to change the system.

  2. 2

    Source: a developer. Stimulus: wishes to change the UI. Artifact: the code. Environment: at design time (not while the system runs).

  3. 3

    Response: the modification is made with no side effects. Response measure: in three hours. If the UI is well separated from the rest of the code, the change stays small and the measure is met.

Exam angle

PredictionQ1

Write a modifiability scenario in which a developer must add a new payment method.

Show answer

Source: developer. Stimulus: needs to add a new payment method. Artifact: the payment module code. Environment: design/development time. Response: the method is added and tested without changing other modules (no side effects). Measure: within 2 person-days, touching no more than one module.

Slide 12 / 18

Quality Attribute Considerations Scenario

Notes

  1. 1

    A general scenario lists the possible values of each part for one quality (here availability). A concrete scenario then picks one value per part.

  2. 2

    Source: internal to the system (a software bug, a memory leak) or external (a power outage, a hacking attempt).

  3. 3

    Stimulus (the fault): crash (sudden failure), omission (no response when one was expected), timing (response at the wrong time), no response, or an incorrect response.

  4. 4

    The rest of the picture:

    Artifact
    The system’s processors, communication channels or persistent storage.
    Environment
    Normal operation, start-up, shutdown, repair mode, degraded (fail-safe) mode, overloaded operation.
    Response
    Prevent the failure, log it, notify users or operators, disable the source of the failure, or be temporarily unavailable.
    Measure
    Time interval available, availability %, detection time, repair time, degraded-mode time interval, unavailability time.
  5. 5

    The handwritten notes show one concrete pick: hardware failure → primary server crash → normal operation → switch to a backup server → restored in 30 seconds.

Exam angle

Past exam · Final 252 · Q3-2 · 2 marksQ1

Construct one quality attribute general scenario for availability.

Show answer

Source: heartbeat monitor (internal to the system). Stimulus: a server becomes unresponsive (crash/omission). Environment: normal operation. Artifact: the server process. Response: detect the fault, notify the operator, disable the failed source and switch to the backup, then repair it. Response measure: failover within 3 seconds; repair time under 30 minutes; 99.9% availability. All six parts with a measurable response measure earn the marks.

Past exam · Quiz 1 · 261 · Q25 (matching)Q2

Availability scenario: “A monitoring service detects that the primary application server has stopped responding during normal operation. The system redirects requests to a standby server and restores service within 30 seconds with no more than 0.1% failed requests.” Match the six elements.

Show answer

Source: monitoring service. Stimulus: detects the primary application server has stopped responding. Artifact: application service/server infrastructure. Environment: normal operation. Response: redirects requests to a standby server and restores service. Response measure: restored within 30 seconds with no more than 0.1% failed requests.

Slide 13 / 18

Quality Attribute Considerations Tactics

Notes

  1. 1

    Architects have a collection of primitive design techniques for achieving a quality attribute response.

  2. 2

    These architectural design primitives are called tactics. A tactic targets one quality response (Chapter 2: a tactic is a design decision that controls a quality attribute response).

  3. 3

    Like design patterns, tactics are proven techniques experienced architects have used for years; we capture them and apply them. Lecture 2 lists tactics for each major quality.

Slide 14 / 18

Extra Examples of Tactics

Notes

  1. 1

    Redundancy (availability): run multiple instances of critical components so that if one fails another takes over. Stimulus: hardware failure or network outage. Response: automatic failover to the backup.

  2. 2

    Caching (performance): keep frequently accessed data in fast temporary storage. Stimulus: many read requests. Response: serve from the cache instead of fetching from primary storage, which cuts response time and load.

Slide 15 / 18

Quality Design Decisions

Notes

  1. 1

    Architecture design is a systematic way of making design decisions, and every quality is achieved through them. They fall into seven categories.

  2. 2

    The first three are about the system’s parts: allocation of responsibilities (which element does which function), the coordination model (how elements interact) and the data model (data abstractions, their operations and properties).

  3. 3

    The last four: management of resources, binding time (how and when elements are bound), choice of technology, and mapping among elements (modules to run-time elements). Slides 16–17 give an example of each.

Exam angle

PredictionQ1

List the seven categories of quality design decisions.

Show answer

Allocation of responsibilities, coordination model, data model, management of resources, binding time decisions, choice of technology, mapping among architectural elements.

Slide 16 / 18

Extra: Quality Design Decisions explained

Notes

  1. 1

    Allocation of responsibilities: deciding which part handles which task. In a shopping app, one part handles logins, another the cart, another payments.

  2. 2

    Coordination model: how the parts communicate and work together, e.g. how the payment system tells the inventory system an item was bought (direct call? event? message queue?).

  3. 3

    Data model: which data the system uses, how it is organised and accessed, e.g. a Customer object with name, address and order history.

Slide 17 / 18

Extra: Quality Design Decisions explained (cont.)

Notes

  1. 1

    Management of resources: how memory, CPU time and network bandwidth are used and allocated, e.g. making sure there is enough server capacity during peak traffic (a performance decision).

  2. 2

    Mapping: how code modules correspond to run-time elements (processes, tasks), e.g. which services run when the UI module is used.

  3. 3

    Binding time: when something is fixed: at compile time, installation, start-up or run time. Example: is the user’s language chosen at installation or switchable at run time? Later binding gives flexibility (modifiability) at some cost (performance, complexity).

  4. 4

    Choice of technology: languages, databases, platforms, e.g. Python on the server, PostgreSQL, AWS hosting.
