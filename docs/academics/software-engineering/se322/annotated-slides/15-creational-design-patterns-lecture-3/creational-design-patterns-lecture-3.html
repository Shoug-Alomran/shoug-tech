Overview

Creational Patterns III: Builder and Singleton

After revising Abstract Factory and Factory Method, the lecture adds two creational patterns. Builder separates the step-by-step construction of a complex object from its representation: a Director calls the same build steps in order, and each ConcreteBuilder implements them differently (C++ vs. Java code, beef vs. chicken burger), returning the product at the end. Singleton ensures a class has only one instance with a global access point: private static instance, private constructor, public static getInstance(). A Prototype exercise (copying shapes with clone()) closes the creational patterns.

Builder roles

Director (runs the steps in order), Builder interface (buildPartA/B/C, getResult), ConcreteBuilders (one per representation), Product.

Builder vs. Abstract Factory

Builder builds one complex object step by step; Abstract Factory creates a family of related objects all at once.

Singleton recipe

Private constructor, private static instance field, public static getInstance() that creates the instance once and returns it.

Prototype

Objects copy themselves with clone() instead of being created with new.

The Builder Pattern

Notes

  1. 1

    The Builder’s intent: separate the construction of a complex object from its representation…

  2. 2

    …so that the same construction process can create different representations. The steps (the algorithm) stay fixed; what each step produces varies with the builder.

Past exam · Final 252 · Q6-1 · 3 marksQ1

Customized sandwiches must follow a correct, consistent assembly process; a Sandwich cannot be created until at least the bread and meat are set, and construction is separate from the Sandwich itself. Which pattern would you use? Draw its class diagram.

Show answer

Pattern: Builder. It separates the construction of a complex object from its representation and builds it step by step. SandwichBuilder (interface): setBread(), setMeat(), setCheese(), build(). CustomSandwichBuilder: stores the parts; build() refuses to create the Sandwich unless bread and meat are set (consistency). SandwichDirector: runs the steps in the correct order. Sandwich: the product (bread, meat, cheese). Diagram: Director → (directs) SandwichBuilder; CustomSandwichBuilder ⇢ realizes SandwichBuilder and creates Sandwich.

Slide 9 / 43

Extra: Builder pattern in one slide

Notes

  1. 1

    Intent: separate how a complex object is built (the steps) from what the result looks like (the representation).

  2. 2

    When useful: same construction steps, different outputs, e.g. generating Java vs. C# code, or a small vs. large burger.

  3. 3

    Roles: Director (orchestrates the steps in order, knows no details); Builder interface (declares the step methods buildPartA/B/C… and getProduct()); ConcreteBuilders (implement the steps for each representation); Product (the thing built).

  4. 4

    Flow: the client chooses a ConcreteBuilder and gives it to the Director → the Director runs the steps in sequence → the client asks the builder for the finished product.

  5. 5

    Builder vs. Abstract Factory: Builder builds one complex object step by step; Abstract Factory creates a family of related objects all at once.

Exam angle

PredictionQ1

Show answer

Extra: Builder Pattern – how to solve

Notes

  1. 1

    0) Recognise a Builder problem: the same sequence of steps must give different final representations; a complex object is built step by step; construction should be hidden from the client and new variants easy to add.

  2. 2

    1) Define the product: name what is built (Report, Burger, Form, House) and list its parts.

  3. 3

    2) Declare the builder interface: the multistep API (buildPartA(...), buildPartB(...), getResult()). Steps say what to build, not how.

  4. 4

    3) Implement concrete builders: one class per variant (PdfReportBuilder, HtmlReportBuilder), each storing intermediate state; getResult() returns the finished product.

  5. 5

    4) Create the director (optional but recommended): a construct() method calls the steps in sequence, keeping the process reusable and consistent. 5) Client wiring: pick a ConcreteBuilder, pass it to the Director, call construct(), get the product.

  6. 6

    6) Verify extensibility: a new variant needs only a new ConcreteBuilder; client and director stay unchanged.

Extra: Builder code skeleton

Notes

  1. 1

    The skeleton in Java:

    CodeWhat it does
    class Product { /* the final object being built */ }1. The product.
    interface Builder { void buildPartA(); void buildPartB(); Product getResult(); }2. The builder interface.
    class JavaBuilder implements Builder { buildPartA() { /* step A for Java */ } … getResult() { return new Product(); } }3. Concrete builders (CSharpBuilder the same, with C# steps).
    class Director { private Builder builder; Director(Builder builder) { this.builder = builder; }4. The director receives a builder…
    Product construct() { builder.buildPartA(); builder.buildPartB(); return builder.getResult(); } }…and runs the steps in a fixed order.
    Builder javaBuilder = new JavaBuilder(); Director director = new Director(javaBuilder); Product javaProduct = director.construct();5. The client chooses the builder; C# is the same three lines with CSharpBuilder.
  2. 2

    Points to remember: product = the final object; builder interface = declares the steps; concrete builders = implement them differently; director = controls the order; client = chooses the builder. Same construction steps, different final representations.

The Builder provides the following benefits

Notes

  1. 1

    It separates construction from representation, so new representations (a C# builder) are added easily.

  2. 2

    Existing representations change without touching the creational process (the director).

  3. 3

    It gives finer control over construction: parts of an object are created at discrete points in time, unlike Abstract Factory, which creates each product in one call.

  4. 4

    It improves maintainability, testability and reusability.

Extra: Builder in simple words

Notes

  1. 1

    In simple words: use Builder when an object is created step by step instead of all at once, like ordering food where you pick bread, meat and sauce and the meal is assembled.

  2. 2

Singleton Design Pattern

Notes

  1. 1

    The UML, member by member. -Singleton(): a private constructor (minus sign) restricts instantiation, so no other class can call new Singleton().

  2. 2

    -instance : Singleton (underlined): a private static attribute that holds the one instance. Underlined members are static in UML.

  3. 3

    +getInstance() : Singleton (underlined): a public static method that creates the instance if needed and gives everyone access to the one and only object. +operation() stands for the class’s ordinary behaviour.

Exam angle

Past exam · Final 252 · Q6-2 · 2 marksQ1

Draw the standard class diagram of the Singleton pattern and convert it into code (any language).

Show answer

Diagram: class Singleton with - instance: Singleton {static}, - Singleton(), + getInstance(): Singleton {static}. Code: public class Singleton { private static Singleton instance; private Singleton() { } public static Singleton getInstance() { if (instance == null) { instance = new Singleton(); } return instance; } }. The private constructor stops other classes calling new; the instance is created on first use and the same one is returned afterwards.

Singleton Design Pattern Example

Notes

  1. 1

    The problem: an application needs event logging. Many objects generate events (actions, status, errors).

  2. 2

    The design: one central event manager that every object uses. It creates an event list on instantiation, adds events as they are logged, and writes them to a file at specific points.

  3. 3

    To prevent conflicts (two managers writing the same file), there must be only one instance of the event manager at any time: Singleton.

Slide 29 / 43

Extra: Why Singleton?

Notes

  1. 1

    Why there is a problem: login, payment and notification systems all need to log. If each creates its own logger, you get multiple log files or conflicting writes, inconsistent data, and a system that is harder to debug and audit.

  2. 2

    The real problem is conflicts, redundancy and loss of control.

  3. 3

    Singleton fixes it: only one EventManager exists, every part shares it, so there is one log file and central control. One object → one responsibility → no conflict.

Singleton Design Pattern Example

Notes

    1. Make the constructor private.

  2. 2

    2. Define a private static attribute that stores a reference to the one instance.

  3. 3

Slide 34 / 43

Benefits of the Singleton Design Pattern

Notes

  1. 1

    Benefit: controlled access to a single instance of a type.

  2. 2

    Benefit: it can be customised to allow a variable number of instances (e.g. a pool of at most N), since creation goes through one method.

  3. 3

    Drawback: it doesn’t work well in multithreaded environments: two threads calling getInstance() at the same moment can both see instance == null and create two objects, unless the method is synchronised.

Exam angle

PredictionQ1

True or false: a Singleton’s constructor should be public so the instance can be created when needed.

Show answer

False — It must be private; clients get the instance through the public static getInstance().

PredictionQ2

Why can the lazy Singleton fail in a multithreaded program, and how is it fixed?

Show answer

Two threads can call getInstance() at the same time, both find instance == null and both create an object. Fix: synchronise getInstance() (or use eager initialisation / double-checked locking).

Extra: Real-World Scenario – banking logger

Notes

  1. 1

    The scenario: a banking app’s login, transaction and notification systems all log events, and everything must go to one log in the correct order.

  2. 2

    Step 1, the Singleton class:

    CodeWhat it does
    public class EventLogger { private static EventLogger instance;The one instance.
    private EventLogger() {}Prevents outside creation.
    public static EventLogger getInstance() { if (instance == null) { instance = new EventLogger(); } return instance; }The global access point, created on first use.
    public void log(String message) { System.out.println("Log: " + message); } }In real use this would write to a file.
  3. 3

    Step 2, the login system: EventLogger.getInstance().log("User " + username + " logged in.");. Why not instance.log()? Because instance is private and static inside the class; from outside, getInstance() is the public way to reach the one object, and then you call .log() on it.
