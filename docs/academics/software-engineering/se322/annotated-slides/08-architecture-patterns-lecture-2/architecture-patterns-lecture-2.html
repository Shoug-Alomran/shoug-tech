Overview

Data-Centered, Data-Flow and Distributed Patterns: Blackboard, Pipes-and-Filters, Client-Server, Broker

Four patterns for three system types. Data-centered systems revolve around shared data: in the blackboard pattern, independent knowledge sources (agents) improve a shared solution on the blackboard while a controller decides who works next. Data-flow systems move and transform a stream: pipes-and-filters chains independent filters with pipes from a data source to a data sink. Distributed systems spread work over the network: client–server is direct and tightly coupled, and the broker pattern puts a mediator (with client- and server-side proxies) between them to loosen that coupling.

Blackboard

Blackboard (shared data) + agents/knowledge sources (independent specialists) + controller (schedules them). Opportunistic: no fixed order of steps.

Pipes and filters

Data source → filter → pipe → filter → … → data sink. Filters are independent, so they can be added, reordered, reused and run in parallel.

Client–server

Clients request, a central server provides. Interoperable and easy to update centrally, but clients are tightly coupled to the server.

Broker

Client → client proxy → broker → server proxy → server. Clients need only the broker, so servers can move or change.

Slide 6 / 48

Blackboard Architectural Pattern

Notes

  1. 1

    The blackboard pattern decomposes a system into components that work around a central data component to solve complex problems.

  2. 2

    The components work independently, each providing a partial solution, in an opportunistic way: whoever can contribute something useful given the current state does so.

  3. 3

    There is no predetermined sequence of operations that leads to the answer. That is the key difference from pipes and filters, whose order is fixed.

Exam angle

Past exam · Midterm 252 · Q5a · 1 markQ1

Best Flight Itinerary system (Midterm 252): a Passenger App sends a trip request to the Trip Planning Service, which creates an empty itinerary draft in the Draft Itinerary Record. The Route Builder lists possible routes, the Constraint Checker filters out routes that break the passenger’s or airline’s rules, and the Best Option Selector picks the best one; each step retrieves the current draft, improves it and saves it back, until the draft is stable and the service returns it to the app. Write the name of the most suitable architectural pattern for this system.

Show answer

Blackboard. Several independent components (Route Builder, Constraint Checker, Best Option Selector) repeatedly read and update one shared data store (the Draft Itinerary Record) until the solution is stable, and a controller (the Trip Planning Service) decides which one runs next. Pipe-and-filter is the tempting wrong answer: there, filters pass output directly to the next filter and no shared store is repeatedly updated.

Slide 7 / 48

Blackboard Architectural Pattern

Notes

  1. 1

    The pattern copies how a group of scientists would attack a hard problem together at one blackboard.

  2. 2

    A mediator (controller) controls access to the board. When it hands control to a scientist, that scientist looks at the current state and, if possible, advances the solution before releasing the board.

  3. 3

    With the new knowledge on the board, control goes to the next scientist who can improve it, and so on until no more progress can be made. There is no fixed order: each contributes when the current state makes their expertise useful.

  4. 4

    This is how expert systems work (AI that applies knowledge and inference rules like a human expert, in medicine or finance), so the blackboard pattern is a good fit for their logical architecture.

Slide 13 / 48

Extra: Blackboard roles and interfaces

Notes

  1. 1

    Who does what: the blackboard is the shared store with a read/write/update API; agents are specialised solvers that use that API when invoked; the controller (scheduler) orchestrates when and which agent runs, and does not pass data around.

  2. 2

    One cycle: (1) the controller decides “Agent A runs now” and calls AgentA.run(); (2) A reads what it needs from the blackboard; (3) A computes and writes its results back; (4) the controller checks the board (or is notified) and picks the next agent.

  3. 3

    Interfaces: the blackboard provides the data API (agents and controller require it); agents provide a service interface such as run() (the controller requires it); the controller generally provides nothing to agents.

  4. 4

    Guideline: control flows controller → agents (invocation); data flows agents ↔ blackboard (read/write). Agents never talk to each other; they communicate only through the blackboard, and only when scheduled.

Slide 18 / 48

Blackboard Architectural Pattern

Notes

  1. 1

    Modifiability: agents are independent, so adding or removing one is easy, e.g. a new SportsSchedule agent without touching the others.

  2. 2

    Reusability: specialised agents can be reused elsewhere, e.g. StudentHistory in a graduation checker.

  3. 3

    Maintainability: knowledge is separated, so fixing a bug in CourseOfferings doesn’t touch WorkSchedule. (The cost: the controller’s scheduling makes behaviour harder to predict and test.)

Extra: Deployment vs. Component Diagram

Notes

  1. 1

    A deployment diagram shows the physical deployment of artifacts (programs, libraries) onto hardware: servers, devices, run-time nodes and the communication links between them. Web-app example: how the web server, application server and database server are configured and connected.

  2. 2

    A component diagram shows how software components are organised and depend on each other through interfaces. Web-app example: the authentication library, data-access objects and business logic, and how they interact. Component = logical structure; deployment = where it runs.

Slide 25 / 48

Data Flow Systems

Notes

  1. 1

    Worker components abstract the transformations applied before data is forwarded: encryption/decryption, compression/decompression, changing format (binary to XML, raw data to information), enhancing, modifying or storing data.

  2. 2

    Transport components abstract how data is moved and controlled. The data-flow pattern studied here is pipes and filters: filters are the workers, pipes the transport.

Slide 26 / 48

Pipes-and-Filters Architectural Pattern

Notes

  1. 1

    Data source: produces the input data.

  2. 2

    Pipes: carry data from one step to the next.

  3. 3

    Filters: process the data (transform, clean, analyse) and pass it on. In the diagram data branches: Filter 1 feeds Filters 2, 3 and 4, which rejoin at Filter 5.

  4. 4

    Data sink: the final destination where the processed data is stored or used.

  5. 5

    Important: the box-and-line diagram is not UML and hides how pipes really work; in real systems pipes can be function calls, files, queues or sockets.

Exam angle

Past exam · Final 252 · Q4-2 · 2.5 marksQ1

StreamFlow: a desktop app for broadcasters processes live video in real time. Frames are modified as they pass through the application before being sent to the streaming server, through transformations in a specific order: Noise Reduction, Color Grading, Watermarking and Compression. Identify the architecture pattern and draw its component diagram.

Show answer

Pipe-and-filter. Each transformation is an independent filter; frames flow between them through pipes in a fixed order, so filters can be replaced or reordered without touching the others: Live feed (source) → Noise Reduction → Color Grading → Watermarking → Compression → Streaming server (sink).

Notes

  1. 1

    Example 1: a language processor (compiler or interpreter) is the classic pipes-and-filters system: source code flows through lexical analysis, parsing, code generation and optimisation.

Slide 29 / 48

Pipes-and-Filters – Example 1: language processor

Notes

  1. 1

    Lexical analyser (filter 1): breaks source code into tokens. int x = 5; becomes int, x, =, 5, ;.

  2. 2

    Parser: builds a parse tree from the tokens (a declaration node for int x, an initialisation node for = 5). Code generator: turns the tree into machine code or an intermediate form (allocate memory for x, move 5 into it).

  3. 3

    Optimizer: makes the code faster or smaller (e.g. one instruction that both reserves and initialises x). In an interpreter pipeline the last filter executes the intermediate form directly instead. The diagram shows that filters are reusable: the same lexer and parser serve both pipelines.

Slide 36 / 48

Pipes-and-Filters

Notes

  1. 1

    Extensibility: add new filters easily (a spam filter). Efficiency: filters can run in parallel. Reusability: filters are reused across systems. Modifiability: add, remove or change filters independently. Security: security filters can be inserted anywhere in the chain. Maintainability: independent filters make updates simple. Trade-off: every boundary needs agreed data formats, and the pattern suits batch-like flows, not interactive ones where the user steers the work midway.

Any three of: extensibility (new filters), efficiency (filters run concurrently), reusability, modifiability (add/remove/reorder filters), security (insert security filters), maintainability.

Distributed Systems

Notes

  1. 1

    Distributed systems are decomposed into multiple processes that usually collaborate over a network.

  2. 2

    Client–server: client-side processes work for users and act as a bridge to a remote server that does the work delegated to it.

  3. 3

    Peer-to-peer: peer nodes with similar capabilities collaborate as equals, e.g. music-sharing applications. The pictures contrast a mesh of peers with a star around one server.

  2. 2

Distributed Systems

Notes

  1. 1

    Examples: Internet systems, web services, file- and music-sharing systems, high-performance computing.

  2. 2

    Common patterns: client–server (clients request, a central server provides, e.g. browser and web server) and broker.

  3. 3

Exam angle

PredictionQ1

How does peer-to-peer differ from client–server?

Show answer

In client–server, clients request services from a central server. In peer-to-peer every node acts as both client and server and they collaborate without relying on one central node, so the system keeps working when any single peer leaves.

Client-Server Pattern

Notes

  1. 1

    Server: a program or device that provides functionality to other programs or devices, its clients.

  2. 2

    Client: hardware or software that accesses a service the server makes available. Many independent clients talk to the server, and clients do not talk to each other.

Broker Pattern

Notes

  1. 1

    The broker pattern gives more flexibility between clients and servers in a distributed environment by acting as a mediator between them.

  2. 2

Slide 45 / 48

Broker Pattern components

Notes

  1. 1

    Client: uses services of one or more servers. Provides nothing; requires the client proxy.

  2. 2

    Client proxy: makes remote components look local to the client (transparency). Provides a local service to the client; requires the broker.

  3. 3

    Broker: mediates between client and server components. Provides mediation to the client proxy; requires the server proxy.

  4. 4

    Server proxy: makes remote components look local on the server side. Provides a local service to the broker; requires the server.

  5. 5

    Server: provides the real application services (it may also act as a client of the broker).

  6. 6

    Bridge (optional): connects different brokers so they can interoperate.

Slide 46 / 48

Broker Pattern

Notes

  1. 1

    The client-side proxy decides whether a request can be resolved locally or must be forwarded to the broker.

  2. 2

    The pattern separates communication functionality from application functionality: everything about networks and messages sits in the broker and proxies, so clients and servers contain only application logic.

  3. 3

    Reading the detailed class diagram:

    Client-side proxy
    packData(), unpackData(), sendRequest(), return(): marshals requests into messages and results back out.
    Broker
    registerService(), findServer(), findClient(), forwardRequest(), forwardResponse(): knows where services are and routes messages.
    Server-side proxy
    packData(), unpackData(), callService(), sendResponse(): calls the real service.
    Client / Server / Bridge
    The client calls callServer() via the broker API; the server registerService()s and runService()s; the bridge transmits messages between brokers.
