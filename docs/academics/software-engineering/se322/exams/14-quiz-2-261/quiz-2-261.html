Q1

Patient admission board

UML

A hospital system models patient admission with this single class:

Given design

Task: Identify the violated SOLID principle, explain why, and draw the corrected class diagram.

Show answerHide answer
SRP: Single ResponsibilityBonus: OCP on notifications

Why: PatientAdmissionBoard has several reasons to change. A change to admission rules, the invoice format, the notification channel or the report layout would each mean editing the same class. Admitting patients, billing, notifying and reporting are separate responsibilities.

Fix: Keep only the admission job in the admission class. Move invoicing, notifications and reporting into their own classes, each of which uses the admission data. Making notifications an interface also allows new channels without modifying anything.

Corrected design

Arrows: the three helper classes have a dashed open arrow (dependency) to PatientAdmission, because they receive it as a parameter. SmsNotification and EmailNotification have a dashed line with a hollow triangle (realization) to the interface.

Q2

Booking service: paper vs digital tickets

UML

A booking service checks availability and issues a ticket. It currently uses a paper-based ticket class. The business now wants to offer digital tickets as well.

Given design

Task: Identify the violated SOLID principle, explain why, and redesign it so new ticket types can be added.

Show answerHide answer
OCP: Open-ClosedDIP: Dependency Inversion

Why (OCP): to add digital tickets you would have to modify BookingService, which already works, instead of extending the system with a new class.

Why (DIP): BookingService is a high-level class that depends directly on the concrete class PaperTicket rather than on an abstraction.

Fix: Add an interface TicketIssuer with issue(). PaperTicket and DigitalTicket implement it. BookingService's field changes type from PaperTicket to TicketIssuer.

Corrected design
interface TicketIssuer { void issue(Booking b); }

class PaperTicket   implements TicketIssuer { public void issue(Booking b) { /* print */ } }
class DigitalTicket implements TicketIssuer { public void issue(Booking b) { /* email / app */ } }

class BookingService {
    private TicketIssuer issuer;
    BookingService(TicketIssuer issuer) { this.issuer = issuer; }
    void book(Booking b) { /* check availability */ issuer.issue(b); }
}

Exam point: adding an SMS ticket later is just one new class, and BookingService never changes. Write that sentence, because it shows the examiner you understand why the fix works.
