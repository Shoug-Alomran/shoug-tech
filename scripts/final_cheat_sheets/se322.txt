== ch1 | 190 | Ch 1 | CH 01 | Introduction to software design
[grid]
[card Design basics]
- Software engineering (IEEE): a **systematic, disciplined, quantifiable** approach to development, operation and maintenance.
- Design as a **process** (activities before construction) vs as a **product** (the artifacts, e.g. class diagrams).
- **Architecture:** macro-design, black-box, major components, mostly **quality** requirements. **Detailed design:** component internals, white-box, mostly **functional** requirements.
- Major activities: architecture, detailed design. Supporting: construction design, HCI design, documentation, management.
[/card]
[card Eight design principles]
Modularization · abstraction · encapsulation · coupling · cohesion · separation of interface and implementation · completeness · sufficiency.
!hook "My Aunt Eats Cake Carefully, Saving Cherries Separately".
[/card]
[card Abstraction (repeated)]
Focus on essential characteristics, defer details. Modularization says **what** to separate; abstraction says **how**.
- **Functional (procedural):** a named operation, e.g. SEND.
- **Data:** a named data type with its operations, e.g. MESSAGE.
- Encapsulation **enforces** abstraction: private fields, public methods.
[/card]
[card Completeness vs sufficiency]
- **Completeness:** the module provides every service it should (no less).
- **Sufficiency:** it provides only what is needed (no more).
[/card]
[card Separation of interface and implementation]
Encapsulation hides the implementation; separation lets **several implementations** sit behind one stable interface (swap them without touching clients).
[/card]
[card Problem solving]
- States: initial (interpret) → operational (generate solutions) → goal (solution chosen, evaluated, validated).
- Six-task framework: interpret, evaluate constraints, brainstorm together, synthesize, evaluate, implement.
- **Functional fixedness:** seeing objects only in their usual role (nine-dots puzzle).
- Challenges: requirements volatility, inconsistent processes, fast-changing technology, managing design influences, ethics.
[/card]
[/grid]
[grid wide]
[card Coupling: worst → best (aim low)]
[table]
Type | Modules share… | Example
Content | One modifies another's internals | Jumps into another module's code or data
Common | Global variables | Both read and write a global config
External | An outside format, protocol or device | Both parse the same file format
Control | A flag telling the other what to do | `process(data, mode=2)`
Stamp | A whole record, only part used | Passing the full Student to read the ID
Data | Only the parameters needed | `computeGPA(grades)`
No coupling | Nothing | Independent modules
[/table]
!hook "Can Cats Eat Chocolate Safely? Definitely Not": content, common, external, control, stamp, data, none.
[/card]
[card Cohesion (aim high)]
[table]
Type | Elements grouped because…
Functional (best) | They all perform one well-defined function
Sequential / procedural | Steps executed in order (output of one feeds the next)
Communicational | They operate on the same data
Temporal | They run at the same time (startup routines)
[/table]
!tip Activity 2 (student registration): modules like Registration, Course Catalog, Payment, Notification. Registration ↔ Payment should use data coupling (pass an amount and student ID), and each module should have functional cohesion.
[/card]
[/grid]
[grid]
[card OO vs structured design]
OO: objects with identity, state, behaviour; inheritance, polymorphism. Structured: top-down functional decomposition, not suited to OO languages.
[/card]
[card Designer roles]
Systems engineer (whole system, hardware + software) · software architect (black-box, quality) · component designer (internals) · UI designer (usability).
[/card]
[/grid]

== ch2 | 205 | Ch 2 | CH 02 | Software architecture, requirements and 4+1
[grid]
[card Definition (five parts)]
Architecture is the **foundational design** (where quality starts), **translates requirements** into traceable models, is a **collection of design elements** (no single diagram), defines **major components and the quality they provide**, and **supports detailed design and construction**.
- Is: communication, what the parts are, how they fit. Is not: development, algorithms, data structures.
[/card]
[card Seven key tasks]
Identify stakeholder concerns · identify architectural views · identify styles and patterns · identify organizational influences · design major components and interfaces · evaluate and validate · set policies for **design synchronicity** (implementation keeps matching the design).
[/card]
[card Requirements engineering]
Elicitation (interviews, facilitated meetings, observation, scenarios) → analysis (classify, prioritize, negotiate, model) → specification → validation.
- Good requirements: specific, correct, complete, consistent, attainable, verifiable.
- Functional vs non-functional; product vs process; imposed vs derived.
[/card]
[card Quality attributes vs tactics]
- Usability, modifiability, security, performance, reliability, portability, testability, availability, interoperability.
- **Tactic** = a design decision that controls a quality attribute's response (caching for performance).
[/card]
[/grid]
### 4+1 view model (repeated)
[table]
View | Shows | Stakeholders | UML diagrams
Logical | Functionality: key abstractions and their relations | End users, analysts, designers | Class, object, sequence, communication, state machine
Process | Runtime behaviour: concurrency, distribution, performance | Developers, system integrators | Activity, interaction overview (sequence)
Development (implementation) | Code organization: modules, layers, packages | Programmers, project managers | Package, component
Physical (deployment) | Mapping of software to hardware nodes | Installers, admins, system engineers | Deployment
Scenarios (+1, use case) | Key use cases that tie and validate the other four | All, especially end users | Use case (with scenarios)
[/table]
!trap Sequence diagrams belong to the logical view in this course's table; activity diagrams to the process view. Component diagrams are development, deployment diagrams are physical.

== ch3 | 150 | Ch 3 | CH 03 | Quality attributes, scenarios and tactics
[grid wide]
[card The six-part quality attribute scenario]
[table]
Part | Meaning | Availability example
Source | Who or what triggers it | Internal hardware
Stimulus | The event | The primary database server crashes
Environment | System state at the time | Normal operation, peak load
Artifact | The part affected | Database tier
Response | What the system does | Detects the failure, fails over to the standby, logs it
Response measure | **Measurable** outcome | Back in service within 30 s, no committed transaction lost
[/table]
!tip "Some source generates a stimulus that arrives at an artifact under some environment, and the system responds; the response is measured." Without a number in the response measure the scenario loses marks.
[/card]
[card More scenario examples]
- **Performance:** users (source) submit 1,000 requests/min (stimulus) under normal load (environment) to the system (artifact); requests are processed (response) with average latency under 2 s (measure).
- **Modifiability:** a developer (source) adds a new payment method (stimulus) at design time (environment) to the code (artifact); the change is made and tested (response) in under 3 person-days with no other module changed (measure).
- **Security:** an unauthorized user (source) tries to read records (stimulus) during normal operation on the patient data (artifact); access is blocked and logged (response), 100% of attempts detected (measure).
[/card]
[/grid]
[grid]
[card Functional requirements vs quality attributes]
Functional: **what** the system does; handled in detailed design. Quality attributes: **how well**; judged on the whole system and decided in the architecture.
[/card]
[card Availability tactics]
- **Detect:** ping/echo, heartbeat, exceptions.
- **Recover:** voting, active redundancy, passive redundancy, spare.
- **Reintroduce:** shadow, state resynchronization, rollback.
- **Prevent:** removal from service, transactions, process monitor.
[/card]
[card Other tactics]
- **Modifiability:** localize changes, prevent ripple effects, defer binding time (config files, runtime plug-ins).
- **Security:** resist (authenticate, authorize, confidentiality, integrity, limit exposure/access), detect (intrusion detection), recover (restore, audit trail).
- **Performance:** resource demand, resource management, arbitration. Measures: latency, deadline, throughput, jitter, miss rate.
- **Testability:** record/playback, separate interface from implementation, built-in monitors.
- **Usability:** separate the UI, support user initiative (cancel, undo), system initiative (models).
[/card]
[card Why scenarios]
QA names overlap and shift meaning: a DoS attack touches availability, performance, security and usability at once. A concrete, measurable scenario pins down what is required.
[/card]
[/grid]

== ch4 | 45 | Ch 4 | CH 04 | Architecture styles and patterns
[table]
System type | Patterns | Cue in a scenario
Data-centered | Blackboard, repository | Shared data store that independent parts read and write
Data flow | Pipes-and-filters | Sequential stages; output of one is input of the next
Distributed | Client-server, broker (peer-to-peer) | Requests over a network; many servers, location transparency
Interactive | MVC | Several views of the same data, UI changes often
Hierarchical | Layered, main program and subroutine | Each level uses only the level below
[/table]
!trap Style = overall template (layered); architectural pattern = system-wide reusable solution (MVC); design pattern = medium scale, one subsystem (Observer).
[grid]
[card Pipes-and-filters]
[calc]
[source] -> | filter | -> | filter | -> | filter | -> [sink]
             pipe        pipe        pipe
compiler: lexer -> parser -> code generator -> optimizer
[/calc]
Filters are independent and only know their input and output. Qualities: **extensibility, efficiency (parallel), reusability, modifiability**, security, maintainability. Weak for interactive systems.
[/card]
[card Blackboard]
[calc]
  [agent 1]   [agent 2]   [agent 3]     (knowledge sources)
       \          |          /
        +---[ BLACKBOARD ]---+          (shared data)
                  |
            [ controller ]              (schedules agents)
[/calc]
No fixed order: agents contribute opportunistically when they can. Expert systems, speech and image recognition.
[/card]
[card MVC]
[calc]
user -> [Controller] --updates--> [Model]
                                     | notifies (Observer)
        [View] <---------------------+
        [View] reads the model and renders it
[/calc]
Qualities: **modifiability, usability, reusability**. Safari Explorer (Final 252): one tour catalogue shown as map, list and booking views.
[/card]
[card Broker]
[calc]
[client]-[client proxy]-[ BROKER ]-[server proxy]-[server]
                           |
                        [bridge] -- another broker
[/calc]
The broker locates servers and forwards requests, so clients reach many servers transparently. Loosely coupled: **interoperability, modifiability, portability, reusability**.
[/card]
[card Client-server and layered]
- **Client-server:** clients request, a central server serves. Interoperability, modifiability, availability, reusability; but clients are **tightly coupled** to the server.
- **Layered:** each layer serves the one above. Modifiability, portability, security, reusability; extra layers can cost performance.
[/card]
[card Activity 5 answers]
Online banking → **client-server**. Image processing stages → **pipe-and-filter**. Speech recognition with independent solvers → **blackboard**. Distributed services found at runtime → **broker**. File sharing without a central server → **peer-to-peer**. UI with several synchronized views → **MVC**.
[/card]
[/grid]

== ch5 | 330 | Ch 5 | CH 05 | Detailed design and SOLID
[grid]
[card Detailed design]
Refines the architecture until it can be built. Tasks: understand the architecture and requirements → create detailed designs (interfaces, GUI, internal component structure and behaviour, data design) → evaluate (technical reviews) → document (SDD) → monitor implementation.
- Class diagram for internal structure, sequence diagram for internal behaviour.
- Common mistakes: depth-first design, refining the SRS directly, ignoring change, over-detailing.
[/card]
[card Abstract class vs interface (repeated)]
[table]
 | Abstract class | Interface
Methods | Abstract and concrete | Abstract only (+ constants)
State | Fields allowed | No instance fields
Keyword | `extends` (one) | `implements` (many)
Use | Shared code in a family | A contract, loose coupling
[/table]
Neither can be instantiated.
[/card]
[/grid]
[table]
Principle | Rule | Classic violation | Fix
**S**ingle Responsibility | One reason to change (one actor) | Person class also validates email; Employee also calculates tax and bonus (Lab 6) | Split: Employee, TaxCalculator, BonusCalculator
**O**pen-Closed | Open to extension, closed to modification | `switch (shape.type)` in drawAllShapes (Lab 5) | Abstract `Shape.draw()`; each shape overrides it
**L**iskov Substitution | Subtypes usable wherever the base is | Square extends Rectangle (setWidth breaks), Penguin extends Bird with fly() | Separate hierarchies or a narrower base (FlyingBird)
**I**nterface Segregation | No client depends on methods it doesn't use | One `IAnimal` with fly(), swim(), roam() | Small interfaces: IFlyable, ISwimmable, IRoamable
**D**ependency Inversion | Depend on abstractions, not details | FundTransferManager uses BankAccount directly (Lab 6); Manager uses Worker | ITransferSource / ITransferDestination; Manager depends on IWorker
[/table]
!trap LSP rule: subtypes may only **weaken preconditions** and **strengthen postconditions**. If a subclass throws "not supported" for an inherited method, LSP is broken.
!tip Answer format: "Violates OCP because adding a Triangle forces a change inside drawAllShapes. Fix: …" then draw the corrected diagram with the abstraction and realization arrows.

== ch6 | 280 | Ch 6 | CH 06 | Creational design patterns
> Purpose classes: creational (creating objects), structural (composing), behavioural (interaction and responsibility). Scope: class (compile time, inheritance) vs object (run time, composition).
[table]
Pattern | Recognise it when… | Not to confuse with
Singleton | Exactly one instance, global access (logger, event manager, config) | –
Factory Method | One product type, subclasses decide which concrete class | Abstract Factory (families)
Abstract Factory | **Families** of related products that must match (per platform or theme) | Factory Method
Builder | One complex object assembled in the **same steps** with different parts | Abstract Factory (builds at once)
Prototype | New objects by cloning an existing one (`clone()`) | –
[/table]
[grid wide]
[card Singleton (Final 252)]
[calc]
+------------------------------+
| Logger                       |
+------------------------------+
| - instance : Logger {static} |
+------------------------------+
| - Logger()                   |
| + getInstance() : Logger     |
+------------------------------+

public class Logger {
    private static Logger instance;
    private Logger() { }
    public static synchronized Logger getInstance() {
        if (instance == null) instance = new Logger();
        return instance;
    }
}
[/calc]
!trap Private constructor + private static field + public static getInstance(). Without `synchronized` two threads can create two instances.
[/card]
[card Builder (computer store / sandwich)]
[calc]
Director ----> <<interface>> ComputerBuilder
 construct()      addCPU() addRAM() addStorage() getResult()
                     ^              ^              ^
             GamingBuilder   OfficeBuilder   ServerBuilder
                         \        |        /
                          ----> Computer (product)

class Director {
    Computer construct(ComputerBuilder b) {
        b.addCPU(); b.addRAM(); b.addStorage();
        return b.getResult();
    }
}
[/calc]
The steps never change; each concrete builder supplies the parts (i9/32GB/1TB vs i5/16GB/512GB). The client only picks the builder.
[/card]
[card Abstract Factory (Lab 7 diagnostics)]
[calc]
<<interface>> TestFactory
  createCPUTest() createMemoryTest() createDiskTest()
        ^                ^                 ^
  PCTestFactory    MacTestFactory    LinuxTestFactory
        |  creates
  PCCPUTest, PCMemoryTest, PCDiskTest   (implement CPUTest,
                                          MemoryTest, DiskTest)
Client holds a TestFactory and the three abstract test types only.
[/calc]
Pros: products always match, new platform = new factory (OCP). Con: many classes; adding a new product type changes every factory.
[/card]
[card Factory Method (ride booking)]
[calc]
abstract RideService                    <<interface>> Vehicle
  bookRide()  { Vehicle v = createVehicle(); ... }
  abstract createVehicle() : Vehicle
        ^           ^           ^
  CarService   BikeService   VanService  ---creates---> Car, Bike, Van

class CarService extends RideService {
    Vehicle createVehicle() { return new Car(); }
}
[/calc]
New vehicle (Bus) = new BusService + Bus; client code unchanged.
[/card]
[/grid]

== ch7 | 20 | Ch 7 | CH 07 | Structural and behavioural design patterns
[table]
Pattern | Type | Recognise it when…
Adapter | Structural | An existing class has the wrong interface for the client
Facade | Structural | One simple entry point to a complex subsystem (ShopKeeper)
Composite | Structural | Tree of whole-part objects treated the same way (folders and files)
Observer | Behavioural | One-to-many: when the subject changes, all dependents update
Iterator | Behavioural | Traverse a collection without exposing its structure (hasNext, next)
[/table]
[grid wide]
[card Composite (file explorer, Final 252)]
[calc]
        <<abstract>> FileSystemItem
         + getSize() : long
          ^                 ^
       File               Folder  <>----- children : List<FileSystemItem>
  getSize(){return size}   add(item) remove(item)
                           getSize(){ sum of children.getSize() }
[/calc]
Clients call getSize() on a file or a whole folder the same way. The folder **aggregates** components (diamond on the composite side).
[/card]
[card Observer (Global Weather Sync, Final 252)]
[calc]
<<interface>> Subject              <<interface>> Observer
 attach(o) detach(o) notify()       update(temp, humidity)
        ^                                  ^
 WeatherStation  ---observers--->  PhoneDisplay, WebDashboard
  setMeasurements(){ ...; notify(); }

void notify() { for (Observer o : observers) o.update(t, h); }
[/calc]
Subject and observers stay loosely coupled; add a new display without changing the station. MVC uses Observer between model and views.
[/card]
[card Adapter: object vs class]
[calc]
Object adapter (composition, preferred)
  Client -> <<interface>> NotificationSystem
                 ^ implements
           NotificationBridge  ---has-a--->  LegacyNotifier
           sendNotification(){ legacy.oldSend(format(msg)); }

Class adapter (inheritance)
  NotificationBridge extends LegacyNotifier implements NotificationSystem
[/calc]
Pro: reuse old code without changing it. Con: extra layer of indirection. Class adapter needs multiple inheritance (Java: extend one class + implement an interface).
[/card]
[card Facade and Iterator]
- **Facade:** `ShopKeeper.sellIphone()` hides the Iphone, Samsung and Blackberry subsystem classes; clients get one stable interface, weak coupling.
- **Iterator:** `Iterator { hasNext(); next(); }` + `Aggregate.createIterator()`; supports several traversals of one collection.
[/card]
[/grid]
!tip Pattern recipe for any scenario: 1) name the pattern; 2) map scenario names to roles (WeatherStation = subject); 3) draw interface, concrete classes, arrows (realization dashed with hollow triangle, inheritance solid with hollow triangle, aggregation hollow diamond, dependency dashed arrow); 4) one advantage tied to the scenario.

== ch89 | 262 | Ch 8–9 | CH 08–09 | Architecture evaluation and documentation
[grid]
[card Evaluation methods]
**ATAM** (Architecture Tradeoff Analysis Method), **SAAM** (Software Architecture Analysis Method), **ARID** (Active Reviews for Intermediate Designs). Common point: all use **scenarios** and **quality attributes**.
- Benefits: prioritizes conflicting goals, forces a clear explanation, improves documentation, finds reuse, improves practice.
[/card]
[card ATAM nine steps]
1. Present ATAM
2. Present business drivers
3. Present the architecture
4. Identify architectural approaches
5. Generate the **quality attribute utility tree**
6. Analyze approaches
7. Brainstorm and prioritize scenarios (all stakeholders)
8. Analyze approaches again
9. Present results
!hook Steps 1–6 with the evaluation team and decision makers; steps 7–9 bring in all stakeholders.
[/card]
[card ATAM outputs]
- **Risks** (decisions that may cause problems) and **non-risks** (sound decisions).
- **Sensitivity points:** a decision that strongly affects one quality attribute.
- **Trade-off points:** a decision that affects several attributes in opposite directions (encryption: security up, performance down).
- Utility tree: quality goals at the top, scenarios as leaves rated (H/M/L) by importance and difficulty.
- Lightweight ATAM: small projects, half a day to a day, internal people only.
[/card]
[card Participants and roles]
Evaluation team (3–5), project decision makers, architecture stakeholders. Roles: team leader, evaluation leader, scenario scribe, proceedings scribe, questioner.
[/card]
[card Documenting a view (5 parts)]
Primary presentation · element catalog · context diagram · variability guide · architecture background (rationale).
[/card]
[card Documentation beyond views (6 parts)]
Documentation roadmap · view documentation · system overview · mapping between views · rationale · directory (glossary, index).
- Uses: **education, communication among stakeholders, analysis** of quality attributes.
- Templates: RUP, SEI Views and Beyond. Starting: select views → define stakeholders → their concerns → decide what and how.
- Other view sets: Siemens four views (conceptual, module interconnection, execution, code), SCR (module, process, uses).
[/card]
[/grid]

? Final 252 style :: A streaming service processes each uploaded video through decode → resize → watermark → encode, and wants to add or remove stages easily. Which architecture pattern?
= Pipe-and-filter
+ Sequential independent stages, output of one feeds the next; filters can be added, removed or reordered (extensibility, reusability).

= MVC
+ One model, several synchronized views notified on change; the controller handles input. Modifiability and usability.

? Final 252 style :: A sandwich shop always assembles bread → filling → sauce, but each sandwich type uses different ingredients. Which pattern?
= Builder
+ Same construction steps (director), different representations (concrete builders).

? Final 252 style :: Several dashboards must refresh whenever the weather station records new readings. Which pattern?
= Observer

? Final 252 style :: A file explorer must compute the size of a file or of a folder containing files and folders the same way. Which pattern?
= Composite

? Lab 7 :: Tests must be created per platform (PC, Mac, Linux), always as a matching set of CPU, memory and disk tests. Which pattern?
- Factory Method
- Abstract Factory
- Builder
- Prototype
= b) Abstract Factory
+ A family of related products that must match per platform.

? Lab 5 :: drawAllShapes() uses switch(shape.type) to call drawSquare or drawCircle. Which principle is violated?
= Open-Closed
+ Every new shape forces a change to working code. Give Shape an abstract draw() and loop calling shape.draw().

? Lab 6 :: FundTransferManager calls BankAccount.removeFunds() and addFunds() directly. Which principle, and the fix?
= Dependency Inversion
+ Introduce ITransferSource and ITransferDestination; the manager depends on them and BankAccount implements both (also ISP).

? Practice :: Square extends Rectangle and overrides setWidth to also set the height. Which principle breaks?
= Liskov Substitution
+ Code that sets width 5 and height 4 on a Rectangle expects area 20; with a Square it gets 16.

= Content, common, external, control, stamp, data, no coupling

? Practice :: A module receives an entire Customer record but only reads the email. Coupling type?
= Stamp coupling

? Practice :: Write the response measure for an availability scenario.

? Practice :: In ATAM, a decision that improves security but slows performance is a ______.
= Trade-off point
+ A sensitivity point affects one attribute strongly; a trade-off point affects several in opposite directions.

? Practice :: What do ATAM, SAAM and ARID have in common?
= They all evaluate the architecture using scenarios and quality attributes.
